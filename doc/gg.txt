1. INTRODUCTION                                                     *gg-intro*

gg talks to the GitLab REST and GraphQL APIs and returns plain Lua tables
("models") with GitLab's field names. The API layer has no UI and no user
commands (only |:checkhealth| `gg`). It never runs `git`: pass remote URLs in
and use |gg.context.parse()|. The optional UI layer, |gg-ui|, is built on top
of it and adds |:Gitlab|.

Requirements: Neovim 0.10 or newer, and `curl` on the `PATH`. There are no
other dependencies.

Every call is asynchronous and returns a |gg-task|. Nothing throws: failures
come back as a |gg-error|.
>lua
    local gg = require("gg")
    gg.setup({ hosts = { ["gitlab.example.com"] = { token = os.getenv("GL_TOKEN") } } })

    gg.issues.get({ host = "gitlab.example.com", project = "group/repo", iid = 12 })
      :on_done(function(issue, err)
        if err then return vim.notify(tostring(err), vim.log.levels.ERROR) end
        print(issue.title, issue.state)
      end)
<

2. SETUP                                                            *gg-setup*

gg.setup({opts})                                                  *gg.setup()*
    Applies the configuration. Returns `true`, or `false, err` with a
    `validation` error that names the bad key. On failure the previous
    configuration stays.

    `hosts` is the one setting you must provide. There is no default
    instance, and requests only go to listed hosts; a call to any other host
    is a `validation` error. The other keys are optional, and the values
    below are their defaults:
>lua
    require("gg").setup({
      hosts = { -- required
        ["gitlab.example.com"] = {
          token = "...",          -- or a function returning the token
          -- optional per host:
          base_url = "https://gitlab.example.com", -- default; may include a relative root
          aliases = { "ssh.gitlab.example.com" }, -- other names (SSH host)
          timeout = { total = 120 }, -- overrides
          retry = { max_attempts = 5 },
        },
      },
      -- optional, with these defaults:
      timeout = { connect = 10, total = 60, stall = 30 }, -- seconds
      retry = { max_attempts = 3, base_delay_ms = 500, max_delay_ms = 30000,
                max_retry_after_s = 60 },
      curl = { cmd = "curl" },
      transport = { backend = "curl" }, -- or a backend table (|gg-testing|)
      log = { level = "warn", sink = nil, file = nil },
    })
<
    Host names are bare names ("gitlab.example.com"), without scheme, path
    or port. `base_url` defaults to `https://<host>`.

    Tokens are looked up per request, in this order:
    1. the host's `token` (a string, or a function called for each request)
    2. the `GITLAB_TOKEN` environment variable
    3. none: the request is sent without a token (public data only)

    `timeout.total` limits a whole request (0 = no limit). Downloads and job
    logs have no total limit; they fail after `timeout.stall` seconds without
    progress. `log.level` is one of "trace", "debug", "info", "warn", "error"
    or "off". By default the log is written to `stdpath("log")/gg.log`.
    `log.sink` replaces that with `fun(level, message, fields)`.

gg.config.get()                                              *gg.config.get()*
    A copy of the effective configuration.

gg.config.host({name})                                      *gg.config.host()*
    The effective settings for one host (aliases resolve to their host):
    `{ name, base_url, token, listed, timeout, retry }`. For a bad or
    unconfigured name it
    returns `nil, err`.

gg.config.hosts()                                          *gg.config.hosts()*
    The listed hosts as `{ [name] = { base_url, aliases } }`, the shape
    |gg.context.parse()| accepts as `opts.hosts`.

3. HOSTS AND CONTEXT                                              *gg-context*

Every resource call takes an explicit `host`; there is no "current host".
`project` is a full path ("group/sub/repo") or a numeric ID. Paths are
always URL-encoded for you. With GraphQL, a numeric ID costs one extra
request to look up the path.

The context functions are pure: they never call git, and they return
`nil, err` (a plain `validation` error table) instead of a Task.

gg.context.parse({url}, {opts})                            *gg.context.parse()*
    Parses a git remote URL into `{ host, port, scheme, project, base_url }`.
    It accepts scp-style (`git@host:group/repo.git`), `ssh://` (the port is
    the SSH port and is not part of `base_url`), `https://`, `http://` and
    `git://` URLs, with any depth of subgroups. Credentials in the URL are
    dropped. Pass `{ hosts = gg.config.hosts() }` to resolve aliases and
    relative URL roots.
>lua
    local ctx = require("gg").context
    local r = ctx.parse(remote_url, { hosts = require("gg").config.hosts() })
    -- r.host = "gitlab.example.com", r.project = "group/sub/repo"
<
gg.context.parse_web_url({url}, {opts})            *gg.context.parse_web_url()*
    Parses a GitLab web URL into `{ host, base_url, project, kind, iid | id }`,
    where `kind` is "issue", "merge_request", "pipeline", "job", "milestone",
    "work_item" or "project".

gg.context.parse_ref({ref}, {default_project})         *gg.context.parse_ref()*
    Parses "#12", "!3", "group/repo#12" or "group/repo!3" into
    `{ kind, project, iid }`.

4. TASKS                                                    *gg-tasks* *gg-task*

Every request returns a Task. Use it with a callback, await it in a
coroutine, or cancel it.

Task:on_done({cb})                                           *gg.Task:on_done()*
    Calls `cb(result, err)` once the task settles, always through
    |vim.schedule()| (never synchronously). A cancelled task never calls it.

Task:await()                                                   *gg.Task:await()*
    Inside a coroutine: suspends until the task settles and returns
    `result, err`. Outside a coroutine it returns a `validation` error
    instead of blocking.

Task:cancel()                                                 *gg.Task:cancel()*
    Cancels the task and kills its request. It is idempotent.

Task:is_done(), Task:is_cancelled()                          *gg.Task:is_done()*

gg.task.run({fn}, {...})                                        *gg.task.run()*
    Runs `fn(...)` in a coroutine where tasks can be awaited. Its return
    value `(result, err)` settles the returned task, and a Lua error inside
    `fn` becomes an "unknown" error. Cancelling the run cancels the task
    it is awaiting.
>lua
    local gg = require("gg")
    local t = gg.task.run(function()
      local mr, err = gg.merge_requests.get({ host = h, project = p, iid = 3 }):await()
      if err then return nil, err end
      local checks = gg.mr_checks.get({ host = h, project = p, iid = 3 }):await()
      return { mr = mr, checks = checks }
    end)
<
gg.task.all({tasks})                                            *gg.task.all()*
    Resolves with all results, in order. The first error rejects it and
    cancels the rest.

gg.task.new({producer})                                         *gg.task.new()*
    Builds a task from `producer(resolve, reject, on_cancel)`.

gg.task.resolved({value}), gg.task.failed({err})           *gg.task.resolved()*
                                                              *gg.task.failed()*
    Tasks that have already settled.

gg.task.is_task({v})                                        *gg.task.is_task()*

5. ERRORS                                                 *gg-errors* *gg-error*

Errors are tables `{ kind, status, message, details }`, and `tostring(err)`
gives a readable line. Messages and details are redacted (|gg-security|).

  kind            meaning ~
  auth            401, no signed-in user, or a token function failed
  forbidden       403
  not_found       404, or an object GitLab returns as null
  validation      bad arguments or config; 400/405/406/409/422; mutation
                  payload errors
  rate_limited    429 once the retries are used up (`details.retry_after`)
  timeout         the request or a download stalled past its limit
  network         connection, DNS or TLS failure
  graphql         a GraphQL `errors` array (`details.errors`). When data came
                  back too, it is in `details.partial`, and it is never
                  returned as a success
  unknown         5xx, invalid JSON, anything else

`details` usually holds `method`, `url` (without the query string),
`request_id` and part of the response `body`.

gg.errors.is({v})                                               *gg.errors.is()*
gg.errors.is_cancelled({err})                         *gg.errors.is_cancelled()*
    True for the error a coroutine receives when a task it awaits is
    cancelled by someone else.
gg.errors.new({kind}, {message}, {opts})                       *gg.errors.new()*
gg.errors.wrap({v})                                           *gg.errors.wrap()*
gg.errors.redact({err}, {secrets})                          *gg.errors.redact()*
gg.errors.cancelled()                                    *gg.errors.cancelled()*

Retries: a 429 waits for `Retry-After` (capped by `retry.max_retry_after_s`).
GET requests also retry 502, 503, 504 and network errors with exponential
backoff and jitter. There are at most `retry.max_attempts` attempts.

6. PAGINATION                                                  *gg-pagination*

Every list has two forms:

  list(args, opts)          one page: `{ items, next_cursor }`
                            opts = `{ per_page = 1..100, cursor = "..." }`
  list_all(args, opts)      collect pages: `{ items, truncated }`
                            opts = `{ limit = N, per_page?, on_page? }`

`next_cursor` is an opaque string (nil on the last page); pass it back as
`opts.cursor`. `list_all` requires a `limit`. It never fetches beyond it,
and it sets `truncated = true` when more items exist. `on_page(items)` is
called for each page as it arrives.

Nested lists in a model (an issue's labels, a pipeline's jobs, …) are capped
by GitLab. When something was cut off, the model has
`truncated = { labels = true }` or similar.

7. RESOURCES                                                    *gg-resources*

All functions take `args` with `host` and return a |gg-task|. Unknown
arguments are rejected as `validation` errors. Models use GitLab's field
names and values (statuses are lowercased). The LuaLS annotations in
`lua/gg/models/` list every field.

ISSUES                                                             *gg-issues*

gg.issues.list({args}, {opts})                               *gg.issues.list()*
gg.issues.list_all({args}, {opts})                       *gg.issues.list_all()*
    Issues of `project` or `group` (GraphQL), or of every project the token
    can see when neither is given (REST, with `scope` = "created_by_me" (the
    default), "assigned_to_me" or "all"). The other filters are `state`
    ("opened", "closed" or "all"), `labels` (issues must have all of them),
    `milestone` (a title, "None" or "Any"), `assignee_username` (a name,
    "None" or "Any"), `author_username`, `search`, `iids`, `order_by`,
    `sort` ("asc" or "desc"), `confidential`, `types` and
    `include_subgroups` (groups only, default true). The default `per_page`
    is 50. Items are `gg.Issue`. Their `weight` is always nil: weights are a
    paid-tier field, and GitLab Free has no such field in its schema.

gg.issues.get({args})                                         *gg.issues.get()*
    `{ host, project, iid }`. Resolves with a `gg.Issue` that includes
    `description` and `subscribed`.

gg.issues.by_iids({args})                                 *gg.issues.by_iids()*
    `{ host, project, iids }`. Resolves with `gg.Issue[]`; missing IIDs are
    left out.

gg.issues.create({args})                                   *gg.issues.create()*
    `{ host, project, title, description?, labels?, assignee_ids?,
    milestone_id?, confidential?, due_date?, issue_type?, weight? }`.

gg.issues.update({args})                                   *gg.issues.update()*
    `{ host, project, iid, ... }`. The fields are `title`, `description`,
    `state_event` ("close" or "reopen"), `labels` ({} removes them all),
    `add_labels`, `remove_labels`, `assignee_ids` ({} unassigns everyone),
    `milestone_id` (false removes it), `due_date`, `confidential`,
    `issue_type`, `weight` and `discussion_locked`.

gg.merge_requests.list({args}, {opts})               *gg.merge_requests.list()*

    Merge requests of `project` or `group`. Without either, `scope` picks

    `reviewer_username`, `search`, `iids`, `source_branch`,
    `target_branch`, `draft`, `order_by`, `sort` and `include_subgroups`.

gg.merge_requests.get({args})                         *gg.merge_requests.get()*

gg.merge_requests.by_iids({args})                 *gg.merge_requests.by_iids()*

    `{ host, project, iids }`, at most `SUMMARIES_MAX` (20) IIDs. One GraphQL
    request. Resolves with `gg.MergeRequestSummary[]`: `iid`, `updated_at`,
    `sha`, `head_pipeline` (`gg.Pipeline` with `id`, `iid`, `status`,

gg.merge_requests.create({args})                   *gg.merge_requests.create()*
    `{ host, project, source_branch, target_branch, title, description?,

gg.merge_requests.update({args})                   *gg.merge_requests.update()*
    `{ host, project, iid, ... }`. Takes the same kinds of fields as
    |gg.issues.update()|, plus `target_branch`, `reviewer_ids` ({} removes

gg.merge_requests.merge({args})                     *gg.merge_requests.merge()*
    `{ host, project, iid, sha?, squash?, should_remove_source_branch?,
    merge_commit_message?, squash_commit_message?, auto_merge? }`. If the

8. TESTING WITH THE FAKE BACKEND                                  *gg-testing*

The fake backend replays recorded responses, so your plugin's tests never
touch the network.
>lua
    local gg = require("gg")
    local fake = gg.testing.fake_backend.new({ root = "tests/fixtures" })
    fake:load("graphql/issues/get.json")
    gg.setup({ hosts = { ["gitlab.example.com"] = { token = "test" } },
               transport = { backend = fake } })
    -- ... call gg, then inspect fake:requests() / fake:last()
<
gg.testing.fake_backend.new({opts})            *gg.testing.fake_backend.new()*
    `{ root?, chunk_size? }`. Methods: `:add(fixtures)`, `:load(...)`,
    `:requests()`, `:last()`, `:reset()`, `:unused()`.

gg.testing.fake_backend.read({path}, {root})  *gg.testing.fake_backend.read()*
gg.testing.fake_backend.parse_url({url})  *gg.testing.fake_backend.parse_url()*

A fixture is a JSON object `{ meta, request, response }`, or an array of
them. A REST request matches on `method`, `path` and `query` (exact), or
`query_contains` / `body_contains` (subset). A GraphQL request matches on
`operation` and a subset of `variables`. `response` holds `status`,
`headers`, and `body` or `body_base64`. It can also simulate a failure
(`error = { kind = "timeout" }`) or a `delay` (ms). A fixture is used once
unless it has `"repeat": true`.

9. SECURITY                                                      *gg-security*

- The token is passed to curl through stdin, never on the command line.
- Redirects are followed by gg, and the token is only sent to the host's
  own origin (same scheme, host and port).
- Requests only go to hosts listed in `hosts`, so neither a configured token
  nor `GITLAB_TOKEN` can reach a host taken from an arbitrary remote URL.
- Tokens and other secrets are redacted from errors and logs: GitLab token
  prefixes, `PRIVATE-TOKEN` / `Authorization` values, `private_token=`
  style query parameters, URL credentials, and the exact token of the
  request.
- |:checkhealth| `gg` reports where a token comes from, never its value.

10. UI: ISSUES AND MERGE REQUESTS                                      *gg-ui*

`gg.ui` is an optional UI built on the API above (it uses only `require("gg")`).
It needs the hosts from |gg-setup|; its own options are separate.

                                                                     *:Gitlab*
:Gitlab [project]
    Open the picker over the whole editor, on the issues view (`<Tab>`
    switches to merge requests, see |gg-ui-mrs|). [project] is
    `group/project`, `host/group/project` or a remote URL. Without it, the
    `origin` remote of the current directory is used (`git remote get-url
    origin`, run asynchronously; the only place gg runs git). With several
    configured hosts, name the host.

gg.ui.open({opts})                                               *gg.ui.open()*
    Open the picker from Lua. `{ project?, host?, cwd?, view? }`: `project`
    as for |:Gitlab|; `host` + `project` open that target directly; `cwd` is
    where to look for the git remote; `view` is "issues" (default) or
    "merge_requests". Returns the view (`:close()` closes it).

gg.ui.setup({opts})                                             *gg.ui.setup()*
    Returns `true`, or `false, err` (the previous options stay). Defaults:
>lua
    require("gg.ui").setup({
      limit = 2000,          -- items fetched per state, per view
      page_size = 50,        -- rows per page
      filter_debounce_ms = 50,
      keymaps = {            -- buffer-local; false disables one
        focus_filter = "/", filter_submit = "<CR>", filter_clear = "<Esc><Esc>",
        inspect_issue = "i", inspect_milestone = "I",
        next_tab = "L", prev_tab = "H", next_page = "P",
        next_milestone = "]m", prev_milestone = "[m",
        refresh = "R", close = "q",
        next_view = "<Tab>", prev_view = "<S-Tab>",
        inspect_mr = { "i", "<CR>" }, -- a key or a list of keys
      },
      order = {},            -- { top?, milestones?, issues? } comparators
      on_inspect_issue = function(issue, ctx) end,         -- default: notify
      on_inspect_milestone = function(milestone, ctx) end, -- default: notify
      on_inspect_mr = function(mr, ctx) end,               -- default: notify
      user_colors = {},      -- { ["username"] = "GitlabUser1" } pins a colour
    })
<
    The inspect callbacks get a mapped |gg-issues| model, the issue's
    milestone or a |gg-merge_requests| model, and `ctx = { host, project, close }` (`close()` closes the
    picker first, e.g. before opening a detail window).

Layout                                                          *gg-ui-layout*
    Two floats: the filter prompt on top and the table below. The table
    shows the tabs (Open / Closed / All with counts), a column header, and
    the issues:
    - issues without a milestone come first, each in its own block,
      newest update first;
    - then one block per milestone (due date ascending, none last). The
      left column shows `%name title`, the due text and the milestone's
      real progress (closed/total, from GitLab, all projects of a group
      milestone). Issues inside are sorted by due date, then IID.
    Labels and Assignee columns hide on narrow windows. When no loaded
    issue has a milestone, the milestone column is left out. Pages hold at most
    `page_size` issues; `P` cycles through them and the footer shows
    `[P] Page 2/5`.
    Open and closed issues load in two parallel streams of pages (up to
    `limit` each, recently updated first). The table appears with the first page and grows while
    the rest arrives: the title reads `Table · loading… N`, and the count
    of a tab that is still loading ends in `…`. Until you move, the
    cursor stays on the first row; after that it follows its issue. Once
    loaded, tabs, filter and pages work without further requests. `R`
    reloads and keeps the current rows until each stream has finished.

Filter                                                          *gg-ui-filter*
    Space-separated tokens, all must match, case-insensitive:
      `~name`    a label contains name
      `%name`    the milestone title contains name (`%none`: no milestone)
      `@user`    an assignee username contains user (`@none`: unassigned)
      `#12`      the IID starts with 12
      other      a substring of the title (a number also matches IIDs)
    The prompt shows `matching / total` (in the active tab) while filtering.

Keys                                                              *gg-ui-keys*
    Table: `j` `k` `<Down>` `<Up>` `gg` `G` move between rows only,
    `/` filter, `L` / `H` next / previous tab, `P` next page, `]m` / `[m`
    next / previous milestone, `i` / `I` inspect the issue / its milestone,
    `R` reload, `q` close, `<Tab>` / `<S-Tab>` switch between the issues
    and merge requests views. Filter: `<CR>` back to the table,
    `<Esc><Esc>` clear and go back. Closing either window closes both.

Merge requests                                                   *gg-ui-mrs*
    The second view of the picker (`<Tab>`), in the same windows; each view
    keeps its own tab, filter text, page and selection. One line per merge
    request: `!iid`, title (`[Draft]` first for drafts), source and target
    branch, reviewers, assignee (`+N` for more), the head pipeline's stages
    (`✓` success, `✗` failed, `◐` running, `○` pending, `▸` manual, `⊘`
    canceled, `–` skipped; more than four: the first three and `…`; `—`
    without a pipeline) and the diff (`+added −deleted` and an 8-cell bar).
    Tabs: Open / Merged / Closed / All, recently updated first. Narrow
    windows hide Target, then Reviewers, then the diff bar, then Source.
    Usernames have a stable colour (`GitlabUser1`…`8`, see `user_colors`);
    the signed-in user is bold. `i` or `<CR>` calls `on_inspect_mr`.

    The list loads first (three parallel streams, like the issues). The
    Pipeline and Diff cells of the visible page fill in afterwards with
    |gg.merge_requests.summaries()| (10 merge requests per request, at most
    4 requests at a time) and show `·` until then; the cursor never moves.
    When GitLab has no line counts for a merge request it reports 0 / 0
    with 0 files; those diff cells are counted from the stored diffs
    instead (|gg.mr_changes.diffstat()|, one more request per such MR).
    Results are cached while the picker is open and reused as long as the
    merge request's `updated_at` is unchanged. `R` also refreshes cells
    whose pipeline was still active and cells that failed to load.

    Filter tokens: `!12` the IID starts with 12, `@user` an assignee,
    reviewer or the author (`@none`: unassigned), `~label`, `%milestone`
    (`%none`), `draft`, other text: the title or the source branch.

Highlights                                                  *gg-ui-highlights*
    All groups are defined with `default = true` and link to standard
    groups, so colourschemes can override them:
    `GitlabPickerBorder` `GitlabPickerBorderActive` `GitlabPickerTitle`
    `GitlabPickerFooter` `GitlabPickerPrompt` `GitlabTableBorder`
    `GitlabTab` `GitlabTabActive` `GitlabColumnHeader`
    `GitlabSeparator` `GitlabMilestoneEdge` `GitlabMilestoneEdgeActive`
    `GitlabMilestoneName` `GitlabMilestoneTitle` `GitlabDue`
    `GitlabDueSoon` `GitlabDueOverdue` `GitlabProgressDone`
    `GitlabProgressTodo` `GitlabProgressText` `GitlabIid`
    `GitlabIssueTitle` `GitlabUnassigned` `GitlabEmpty`
    `GitlabStateOpened` `GitlabStateClosed` `GitlabCursorMark`
    `GitlabCursorLine` `GitlabLabelFallback`. Labels use their GitLab
    colour through `GitlabLabel_<hex>` groups.
    Merge requests: `GitlabDraft` `GitlabBranchSource`
    `GitlabBranchTarget` `GitlabUser1` … `GitlabUser8`
    `GitlabCurrentUser` (bold, layered on the user's colour)
    `GitlabPipelineSuccess` `GitlabPipelineFailed` `GitlabPipelineRunning`
    `GitlabPipelinePending` `GitlabPipelineManual` `GitlabPipelineCanceled`
    `GitlabPipelineSkipped` `GitlabDiffAdd` (links `GitlabPipelineSuccess`)
    `GitlabDiffDelete` (links `GitlabPipelineFailed`).
    `GitlabIssueTitle` and `GitlabDue` take only the foreground of
    `Normal`, so the row highlight shows behind them.
    Key hints use `GitlabHintKey` (the `Function` colour, bold) for the
    key and `GitlabHintText` (the `Comment` colour, not italic) for the
    description.
    The table's border is always `GitlabTableBorder`; only the filter's
    border changes colour with focus. Unassigned issues are drawn in
    `GitlabUnassigned` from the IID to the state.
    While the table is focused, the cursor is hidden through 'guicursor'
    with `GitlabHiddenCursor` (`blend = 100`). The row's `▌` mark shows
    the selection instead, and 'guicursor' is restored when you leave.
